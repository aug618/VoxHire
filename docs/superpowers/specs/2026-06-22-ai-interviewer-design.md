 # AI Interviewer Design Spec (v1.0)
 > 2026-06-22 | 经过完整 brainstorming 确定的系统设计文档
 > 本项目为开源项目，旨在打造功能完善的 AI 面试官系统
 ---
 ## 一、项目定位
 - 开源项目，代码完全公开，社区驱动
 - 核心体验：语音 + 虚拟形象实时交互面试
 - 面试类型：以技术面 + 行为面为主，同时支持综合面
 - 用户画像：个人面试练习优先，架构预留企业场景扩展空间
 - 商业化意图：项目成熟后可考虑拉投资、提供企业版
 ---
 ## 二、核心设计决策
 | 决策点 | 选择 | 说明 |
 |--------|------|------|
 | 交互形态 | 语音 + 虚拟形象 | 真人视频流作为后续可选插件 |
 | 面试类型 | 技术 + 行为为主 | 综合面也支持，侧重技术深度和行为评估 |
 | 技术栈 | React/Next.js + Python/FastAPI | 前后端分离，Python 生态做 AI 最顺手 |
 | 部署形态 | Web 应用 + 后续 Electron 壳 | 核心是 Web 应用，本地启服务浏览器访问 |
 | LLM 策略 | 先单 Agent，后多 Agent | MVP 单 Agent Prompt 驱动，架构预留多 Agent 接口 |
 | 评分维度 | 7 维（4 技术 + 3 行为） | 5 级评分 + 行为锚定描述 |
 | 对话记忆 | 混合策略 | 固定头 + 阶段摘要 + 滑动窗口 |
 | STT 方案 | 先句子级，后流式 | MVP 句子级保障稳定，架构留好流式接口 |
 | 对话管道 | LLM 流式 + TTS 分段合成 | 非串行等待，首次响应延迟压缩至 3-5 秒 |
 | Python 环境 | uv 管理 | 项目级虚拟环境（.venv），pyproject.toml 管理依赖，不用全局 conda |
 ---
 ## 三、MVP 功能边界
 ### 包含
 - 语音对话交互（STT 句子级 -> LLM 流式生成 -> TTS 分段合成 -> 边生成边播放）
 - 虚拟形象展示（前端渲染，不涉及视频流）
 - 技术面 + 行为面两种模式
 - 混合策略对话记忆
 - 单 Agent 驱动面试流程
 - 7 维评估报告（4 技术 + 3 行为），带行为锚定描述
 - React/Next.js + Python/FastAPI，Web 应用形态
 - 本地 Ollama 优先，可选配 API 增强
 ### 不做（后续迭代）
 - 真实视频流 / WebRTC
 - 多 Agent 协作
 - 流式 STT
 - 桌面打包（Electron 壳）
 - 企业多用户/管理后台
 - 表情/情感分析
 - Barge-in（用户语音打断 AI）
 - 种子题库（按技术栈+难度分层的面试题库）
 - 面试前破冰/试音环节
 - 中英混杂语音识别专项优化

 ## 四、整体架构
 ```前端 (React/Next.js)
 ├── 面试准备页 — 岗位/范围/资料输入、面试类型选择
 ├── 面试进行页 — 虚拟形象 + 语音对话界面 + 实时字幕
 └── 评估报告页 — 7 维评分雷达图 + 逐项点评 + 改进建议
 后端 (Python/FastAPI)
 ├── REST API — 面试配置、报告查询、资料管理
 ├── WebSocket — 实时对话管道（音频流非视频流）
 └── 会话管理 — 面试状态机 + 混合记忆管理
 AI 管道
 ├── STT (faster-whisper) -> LLM 流式输出 -> TTS 分段合成（边生成边播放）
 ├── 单 Agent Prompt 驱动面试流程
 └── 记忆策略：上下文顶部 [面试要求+候选人背景] + [阶段摘要] + [最近8轮对话]
 部署
 └── Web 应用（本地启动服务，浏览器访问）
     └── Python 环境使用 uv 管理（uv init / uv add / uv run），项目级 .venv
     └── 后续可加 Electron 壳打包桌面版```

 ## 五、核心模块设计
 ### 5.1 面试配置模块
 - 用户输入：岗位名称、技术栈、面试难度（初级/中级/高级）
 - 可选：上传简历/项目经历（PDF 提取内容塞入 prompt）
 - 选择面试类型：技术面 / 行为面 / 混合
 - 模型配置：选本地 Ollama 模型 或填入 API Key 切云端
 ### 5.2 面试状态机
 ```[初始化] -> [开场白] -> [核心问答循环] -> [结束语] -> [报告生成]
               ^              |
               +-- 追问/跳题 --+```
 - 开场白生成：AI 自我介绍、说明面试流程
 - 核心问答循环：出题 -> 听答 -> 判断（对->深挖 / 错->引导 / 一般->追问1-2次->下一题）
 - 时间控制：预计 20-30 分钟，动态调整题量
 - 结束语：感谢 + 说明报告正在生成
 ### 5.3 对话管道模块（流式分段合成）
 ```前端录音 -> WebSocket 发音频
   -> 后端 STT (faster-whisper) 句子级转写
   -> LLM 流式生成（Ollama/API streaming）
   -> 按句子边界切分 token 流
   -> TTS (Edge-TTS) 逐段合成
   -> WebSocket 逐段发送音频
   -> 前端排队播放（边生成边播放）```
 - LLM 流式输出 token，按句子边界（句号/问号/感叹号）切分
 - 每完成一个句子立即送入 TTS 合成，合成完毕即推送前端播放
 - 前端维护音频播放队列，保证语音连续无缝
 - 首次响应延迟 = STT耗时 + LLM首句耗时 + TTS首段耗时，目标 < 3-5 秒
 - 前端展示实时字幕（STT 结果 + AI 回复文字逐句追加）
 - 音频格式统一为 16kHz mono WAV
 - 延迟目标：首次响应 < 5 秒（含 LLM 推理），段间间隔 < 1 秒
 ### 5.4 记忆管理模块
 ```上下文结构 = [
   固定头: 面试要求 + 候选人背景 (始终保留),
   阶段摘要: 每个主题模块的问答摘要,
   滑动窗口: 最近 8 轮完整对话
 ]```
 - 每个主题/题目结束后触发摘要生成
 - Token 预算分配：系统 prompt 30% / 记忆 40% / 当前对话 20% / 输出预留 10%
 ### 5.5 虚拟形象模块
 - 前端渲染，使用 Live2D / VRM 或 CSS 动画驱动
 - TTS 输出时触发口型同步（语音时长驱动）
 - 三种状态：idle（等待）、thinking（思考中）、speaking（讲话中）
 ### 5.6 评估报告模块
 技术面试维度（4 项，5 级评分 + 行为锚定描述）：
 1. 技术准确度 — 回答的核心技术点是否正确、深度如何
 2. 问题解决能力 — 是否系统性分析问题、提出优化方案、正确评估复杂度
 3. 代码/架构质量 — 代码质量、实现准确度、设计取舍合理性
 4. 知识广度 — 相关领域知识覆盖面、横向对比能力
 行为面试维度（3 项，5 级评分 + 行为锚定描述）：
 5. 沟通表达 — 是否清晰组织语言、主动澄清、逻辑严谨
 6. 思维逻辑 — 分析问题的结构化程度、推理是否自洽
 7. 项目经验/综合素养 — 过往经验相关度、团队协作、学习反思能力
 报告输出：
 - 7 维雷达图 + 综合加权评分
 - 逐题点评（回答亮点 + 改进点）
 - 整体改进建议

 ## 六、技术选型（基于 2026 年 6 月调研）
 > 选型原则：本地优先、中文优先、开源优先、延迟敏感。
 ### 6.1 STT 语音识别
 | 方案 | 中文 CER | 速度 | 流式 | 模型大小 | 许可证 | 推荐度 |
 |------|---------|------|------|---------|--------|--------|
 | **FunASR SenseVoice-Small** | **4.2%** | 170x (GPU) | 支持（streaming版） | 254MB | MIT | ⭐⭐⭐⭐⭐ |
 | FunASR Paraformer-zh | ~5-8% | 120x (GPU) | 原生streaming | ~800MB | MIT | ⭐⭐⭐⭐ |
 | faster-whisper large-v3 | ~20% | 12x (GPU) | 需自建VAD | 1.5GB | MIT | ⭐⭐⭐ |
 | whisper.cpp | 22-31% | 10x (CPU) | --stream模式 | 3GB | MIT | ⭐⭐ |
 | Deepgram Nova-3 | 未知 | 云端 | 原生WebSocket | N/A | 商业 | ⭐⭐⭐ |
 **推荐：FunASR SenseVoice-Small 为主力，faster-whisper 为英文场景备选。**
 - FunASR 中文准确率是 Whisper 的 **5 倍**（4% vs 20% CER），这对面试场景至关重要
 - SenseVoice-Small 仅 254MB，CPU 即可 17x realtime，完全满足实时对话
 - 内置完整管道：VAD + ASR + 标点恢复
 - paraformer-zh-streaming 原生流式版本适合实时面试
 - 面试类型为英文时可切换 faster-whisper large-v3（英文准确率更高）
 - 不推荐 whisper.cpp（中文 CER 22-31%）和 WhisperX（已停止维护）
 ### 6.2 LLM 大模型
 **主模型（面试对话）：Qwen3-32B Q4_K_M**
 - 中文对话质量顶级（C-Eval/CMMLU 领先，社区公认中文最强）
 - 128K 上下文窗口，满足 20-30 轮面试对话
 - Ollama 原生支持，RTX 4090 上约 35-38 tok/s
 - 支持 tool calling 和 JSON 结构化输出
 - Apache 2.0 许可证
 **副模型（摘要/评估报告）：Qwen3-8B Q4_K_M**
 - 摘要/评估用，速度约 170 tok/s，5.6GB VRAM
 - 评估报告 JSON 输出建议用 Q5_K_M（更高精度，避免格式错误）
 **双模型同时加载策略（RTX 4090 24GB）：**
 - 方案A：主模型 Qwen3-14B(9GB) + 副模型 Qwen3-8B(5.6GB) = 14.6GB，可同时加载
 - 方案B：主模型 Qwen3-32B(19GB) 单独加载，面试结束后切换副模型
 - KV 缓存优化：`OLLAMA_KV_CACHE_TYPE=q8_0` 可减半缓存占用
 **已知坑：Qwen3.5 的 Thinking 模式在 Ollama 上有无限循环 bug，建议用原始 Qwen3。**
 | 场景 | 模型 | 量化 | VRAM | 速度 |
 |------|------|------|------|------|
 | 面试对话（质量优先）| Qwen3-32B | Q4_K_M | ~19GB | 35-38 tok/s |
 | 面试对话（平衡）| Qwen3-14B | Q4_K_M | ~9GB | 90-100 tok/s |
 | 摘要/评估报告 | Qwen3-8B | Q5_K_M | ~6.6GB | 170 tok/s |
 ### 6.3 TTS 语音合成
 | 方案 | 中文质量 | 首句延迟 | 流式 | 本地 | 许可证 | 推荐度 |
 |------|---------|---------|------|------|--------|--------|
 | **Edge-TTS** | 优秀（XiaoxiaoNeural） | ~200-500ms | 部分支持 | 否（云端） | 灰色 | ⭐⭐⭐⭐（MVP） |
 | **CosyVoice 3** | 极优（母语级，18+方言） | ~150ms (GPU) | 双向流式 | 是 | Apache 2.0 | ⭐⭐⭐⭐⭐（目标） |
 | Fish Speech S2 | 极优（4.51/5.0） | ~100ms | 支持 | 是 | 需授权 | ⭐⭐⭐⭐ |
 | ChatTTS | 优秀（对话韵律） | ~300-500ms | 部分支持 | 是 | AGPL-3.0 | ⭐⭐⭐ |
 | Coqui XTTS-v2 | 中等（口音重） | ~200ms | 支持 | 是 | MPL-2.0 | ⭐⭐（已停维） |
 | Piper TTS | 差（中文不可用） | ~10ms | 否 | 是 | Apache 2.0 | ⭐ |
 | OpenAI TTS | 良好 | ~300-600ms | 支持 | 否 | 商业 | ⭐⭐⭐（备选） |
 **推荐：MVP 先用 Edge-TTS（零成本快速验证），目标方案切换到 CosyVoice 3。**
 - Edge-TTS：`pip install edge-tts`，3 行代码，中文质量优秀，适合快速原型
 - CosyVoice 3（阿里 FunAudioLLM）：中文母语级质量，Apache 2.0，真正双向流式
 - 不推荐 Coqui（公司已关闭）、Piper（中文不可用）、Kokoro（中文弱）
 ### 6.4 虚拟形象
 | 方案 | 类型 | React集成 | 唇语同步 | 许可证 | 推荐度 |
 |------|------|----------|---------|--------|--------|
 | **@met4citizen/talkinghead** | 3D Three.js | 可封装为组件 | 内置viseme | MIT | ⭐⭐⭐⭐⭐ |
 | **@met4citizen/headtts** | 浏览器TTS | 原生 | 输出viseme | MIT | ⭐⭐⭐⭐⭐ |
 | **@met4citizen/headaudio** | 音频→viseme | 原生 | MFCC检测 | MIT | ⭐⭐⭐⭐ |
 | wawa-lipsync | 音频→viseme | 原生 | FFT分析 | MIT | ⭐⭐⭐ |
 | Live2D Cubism SDK | 2D | 需封装 | 内置 | 商业免费tier | ⭐⭐⭐ |
 | VRM + @pixiv/three-vrm | 3D Three.js | 可封装 | 需自建 | MIT | ⭐⭐⭐⭐ |
 **推荐：MVP 使用 CSS 动画（三态），v0.2 升级为 met4citizen/TalkingHead。**
 **重要发现：Ready Player Me 已于 2026 年 1 月关闭**（被 Netflix 收购），不可再用。VRM 格式是替代方案。
 ### 6.5 前后端框架
 | 技术 | 推荐版本 | 说明 |
 |------|---------|------|
 | **Next.js** | 16.2.x | App Router 完全稳定，Async Request APIs 必须用 await |
 | **React** | 19.2.1 | 并发渲染对音频流式 UI 有天然优势 |
 | **Tailwind CSS** | 4.3.x | 新项目直接用 v4，Rust 引擎性能飞跃 |
 | **FastAPI** | 0.138.x | WebSocket 支持成熟稳定 |
 | **Pydantic** | 2.13.x | v2 已完全稳定，Rust 核心 |
 | **uv** | 0.11.x | 生产就绪，10-100x 于 pip |
 | **Node.js** | 24 LTS | 活跃 LTS，支持到 2028 |
 | **Python** | 3.13.x | 生态兼容性最好 |
 ### 6.6 唇语同步方案
 **MVP（v0.1）：** CSS 动画三态（idle/thinking/speaking），不涉及唇语同步
 **v0.2（3D 头像）：** 后端 TTS 音频 + 前端 wawa-lipsync 实时频域分析 → viseme → morph target 驱动
 **v0.3（精确口型）：** CosyVoice 3 返回 phoneme 时间戳 → 后端转换为 Oculus 15 viseme → WebSocket 推送 → 前端精确口型动画
 **viseme 标准：采用 Oculus/Meta 15 viseme**，行业最广泛使用，兼容 ARKit blendshape

 ## 七、非功能需求
 - 可扩展性：各组件可独立替换（如本地模型 -> API），插件机制支持后续功能扩展
 - 性能：音频管道低延迟，LLM 推理响应时间可控
 - 隐私：本地优先，用户数据不上云（除非主动配置 API）
 - 开源友好：清晰的模块边界、完善的开发文档、易上手的贡献流程

 ## 八、体验设计补充建议（MVP 后快速迭代）
 > 以下建议在 MVP 首版不一定实现，但架构层面需预留接口，后续按优先级迭代。
 ### 8.1 沉默检测与结束判定
 **问题：** 句子级 STT 的核心难题——系统如何判断用户"说完了"？
 **方案：** MVP 暂定固定超时（~1.5 秒静音 = 结束）。后续迭代方向：
 - VAD（Voice Activity Detection）+ 静音超时混合策略，提高判定准确率
 - 在 UI 上提供"回答完毕"手动按钮作为兜底，避免长时间静音的尴尬
 - 架构预留：WebSocket 管道中 STT 前置一个 VAD 判断层接口
 ### 8.2 Barge-in（用户语音打断 AI）
 **问题：** 当前管道是单向流水线（STT→LLM→TTS→播放），AI 讲话时用户无法插话。
 **方案：** MVP 不实现。后续迭代方向：
 - 实时检测用户语音输入，打断当前 TTS 播放并重新进入听答流程
 - 前端 audioQueue 清空 + 后端取消当前 LLM 生成任务
 - 架构预留：WebSocket 管道支持"中断"消息类型，前端 audioQueue 提供 clearQueue 接口
 ### 8.3 虚拟形象质量
 **问题：** 三态 CSS 动画（idle/thinking/speaking）可能拉低产品专业感。
 **方案：** MVP 使用 CSS 动画确保可交付。后续迭代方向：
 - 接入免费 Live2D 模型（如 Cubism SDK）或 VRM 格式 3D 头像
 - 加入眨眼、随语音音量微微晃动等微动效
 - TTS 口型同步（phoneme 到 viseme 的映射）
 ### 8.4 面试种子题库
 **问题：** 纯 LLM 动态出题可能质量不稳定（尤其本地小模型），且多次面试题目相似。
 **方案：** MVP 不依赖题库，纯 prompt 驱动。后续迭代方向：
 - 按技术栈 + 难度分层的种子题库（JSON/YAML 格式）
 - 注入 prompt 作为出题参考，LLM 在此基础上变化和追问
 - 支持社区贡献题目，形成开源题库生态
 ### 8.5 面试复盘与对话回放
 **问题：** 报告只有 7 维评分，用户无法回溯当时的具体回答。
 **方案：** MVP 的评估报告页暂不含回放。后续迭代方向：
 - 报告页点击某道题 → 展示完整问答文本（文本回放，低成本高价值）
 - 保留面试音频片段，支持语音回放（需存储管理方案）
 - 将评分和对话内容关联，让用户看到"这个分数对应的原始表现"
 ### 8.6 中英混杂语音识别
 **问题：** 技术面试中候选人常中英混杂说话（如 "我用的框架是 React，它的 virtual DOM 通过 reconciliation 算法..."），小模型可能丢词。
 **方案：** MVP 使用 faster-whisper 默认配置。后续迭代方向：
 - 明确推荐 whisper 模型大小（至少 medium，推荐 large-v3）并标注中英混杂性能
 - 评估 Deepgram 等云端 STT 对中英混杂的支持
 - 专项测试：收集典型中英混杂技术面试语料，评估转写准确率
 ### 8.7 面试节奏控制
 **问题：** 当前 prompt 的追问策略（答对深挖/答错引导/一般追问1-2次）较为机械。
 **方案：** MVP 简单 prompt 策略即可。后续迭代方向：
 - 系统 prompt 中加入节奏控制角色描述："你是经验丰富的面试官，要保持面试节奏的张弛有度"
 - 支持根据候选人表现动态调节题量和难度曲线（如连续答对→适当加难，连续答错→降级安抚）
 - 多 Agent 架构下，可独立出一个"节奏控制 Agent"负责全局调控
 ### 8.8 面试前破冰/试音
 **问题：** 用户直接进入面试可能紧张，且麦克风设备问题会导致前几句话听不清。
 **方案：** MVP 不实现。后续迭代方向：
 - 面试前增加试音环节：让用户对着麦克风说几句，检测音量/设备是否正常
 - 同时起到破冰作用，消除紧张感
 - 试音数据可用于校准 STT 音量阈值（与 VAD 配合）
